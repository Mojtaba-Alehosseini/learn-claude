# Every place a check is run, and how long the build was lying

FIX-31: *"List every invocation of every gate … For each: the command, what it is piped
through, whether its exit status reaches the caller, and whether the caller stops on it."*

This file is the method and the evidence. The two tables it produces are in
`docs/attack/FIX-31.md`.

## How each answer was got, rather than assumed

**Does the status reach the caller?** A pipeline in `sh` and `bash` reports the status of
its **last** command. `cmd | tail -1` therefore reports `tail`'s status, and `tail` does
not fail. That is not a subtlety to be argued about: it was reproduced directly.

```
$ bash -c 'set -e; python -c "import sys; sys.exit(1)" | tail -1; echo "exit=$?"'
exit=0
```

**Does `set -o pipefail` fix it?** For `tail`, yes. For `head`, no - and worse than no:

```
$ bash -c 'set -e; set -o pipefail; python -c "
for i in range(100000): print(i)" | head -3; echo "exit=$?"'
0
1
2
... OSError: [Errno 22] Invalid argument
exit=120
```

`head` closes the pipe after three lines, the producer dies writing to it, and pipefail
reports that as failure. A gate that goes red for a reason unconnected to what it guards is
a gate people learn to ignore, so `build.sh` now pipes nothing: a `gate` helper captures
the output, prints the tail on success and everything on failure, and returns the
command's own status.

**Which runner stops on a failure?** `build.sh` runs under `set -e`, so the first non-zero
status ends it. GitHub Actions ends a job on the first step with a non-zero status. Both
were confirmed by planting a fault - see `scripts/test-gates.py`, which does exactly that
for every gate worth planting one in.

## The hole, stated exactly

Between `9c3d100` (2026-09-05, the commit that added the search suite to `build.sh` behind
`| tail -2`) and `5414d29` (2026-09-06), **no gate in `build.sh` could fail the build.**
Twelve of them accumulated in that window. The generators were unaffected: `stable-ids.py`,
`build-search-index.py`, `build-sitemap.py`, `build-data-js.py` and `measure.py --status`
were never piped, so a build that could not write its data still stopped.

Two gates were piped before that and are not part of the hole, because they are generators
rather than gates: `add-source.py | head -3` and `build-paths.py | tail -3` have been
piped since the first commit of the file.

## The history: how long, and what shipped

`tmp/gate_history.py` takes each round-end commit, checks it out into a temporary git
worktree, and runs **that commit's own** `build.sh` steps in order, each with its pipe and
redirection stripped, continuing past failures so every failing gate is found rather than
only the first.

Running the old file under `bash -o pipefail` was rejected as the method: `head` would
have made several rounds look red for the SIGPIPE reason above, which would have been a
louder answer and a wrong one.

Deployment is not inferred from the table either - it is read from the Actions history for
each commit's SHA.

The result is in the round record. In short: five rounds were genuinely green, one shipped
live with a gate failing, and one was caught by CI because CI happened to run the gate in
question without a pipe.

**Why CI caught the second and not the first.** The deploy workflow does not run every
gate. It runs the catalogue validator, its bite test, `test-measure.py`, the picks
validator and its bite test, `build.sh`, the data-file check, `test-browse-query.js`,
`test-search.py` and `test-copy-claims.py`. It has never run `validate-synonyms.py`,
`test-stem.py`, `test-role-buckets.py`, `check-questions.py`, `test-gap-claims.py`,
`check-typed-numbers.py` or the two advisory audits. `check-typed-numbers.py` is the gate
that was failing at FIX-29, and no runner anywhere could see it. `test-search.py` is the
gate that was failing at FIX-30, and CI ran that one directly.

That asymmetry is now gone from both ends: `build.sh` runs every gate with its status
visible, and CI runs `scripts/test-gates.py`, which plants a fault in each and asserts the
build goes red.

## The other runners

**`check-links.yml`** runs `check-links.py` and `report-dead-links.py` as separate steps
with no pipe. Statuses reach the runner and the job stops on either. The workflow is
deliberately read-only - it opens an issue and never edits `data/` - so a failure here
reports rather than blocks, which is the intent stated in its own header.

**The git hooks.** `.git/hooks/pre-commit` and `.git/hooks/commit-msg` are four-line shell
wrappers generated by `scripts/install-hooks.py`; each `exec`s a script in `scripts/`, so
the script's exit status *is* the hook's, with nothing between them. `pre-commit.py` calls
`validate-catalogue.py` through `subprocess.run` and checks `returncode` explicitly. No
hole. The hooks live in `.git/`, which is not diffed and does not exist on a fresh clone -
that is a different kind of invisibility, and it is why the logic sits in `scripts/` where
it can be read.

## What is still worth knowing

`scripts/test-gates.py` takes about three minutes, because it runs the real build once per
planted fault. That is the price of testing what actually runs rather than a model of it.
It is in CI and deliberately not in `build.sh`: a build that ran it would call itself.
